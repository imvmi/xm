# XM：个人 X 动态归档

Go + SQLite / MySQL 的自部署归档服务，内置中文管理页面，也保留命令行采集工具。使用你自己的 Cookie 和独立的临时 Chrome，读取目标主页实际返回的时间线数据。支持公开账号和**当前登录账号已获准关注**的锁推账号；不提供越权访问、自动关注、自动登录或验证码处理。

支持 Cookie 导入、代理配置、账号管理、定时轮询，以及推文、图片和视频浏览。自动监控以增量边界为主要停止条件，并保留内部安全上限；媒体支持本地、Samba（SMB2/3）、WebDAV 和 S3（含兼容服务），正文与索引默认保存在 SQLite，也支持 MySQL。网页结构变化、登录验证和限流仍可能中断采集。使用网页自动化存在 X 规则和账号限制风险。

## 运行条件

- Go 1.26+（启用 Go 自动工具链下载时，旧版 Go 会按 go.mod 下载所需版本）。
- 本机 Chrome / Chromium。通过 `chrome_path` 指定可执行文件；未设置则自动查找。
- 一个能访问 X 的网络或代理，以及你已登录 X 的 `auth_token`、`ct0`。
- 推荐普通用户运行，保留 Chrome 沙箱。Linux ARM64 也可使用系统 Chromium。

不依赖 Python、Node、FFmpeg、Redis 或系统 SQLite；SQLite 驱动是纯 Go。

### Windows

可交叉编译 Windows x64 可执行文件（编译机需安装 Go，运行机器只需安装 Chrome）：

```bash
GOOS=windows GOARCH=amd64 CGO_ENABLED=0 go build -trimpath -ldflags="-s -w" -o xm.exe ./cmd/xm
```

在 Windows 程序目录运行 `.\xm.exe serve -config config.yaml -listen 127.0.0.1:9980`，
然后打开 http://127.0.0.1:9980。迁移已有归档时先正常停止旧服务，完整复制配置、
SQLite 数据库、媒体和头像，将 `config.yaml` 的 `data_dir` 改为 `./data`。
数据库继续放在本地磁盘；留空 `chrome_path` 可自动查找已安装的 Chrome。
首次启动前核对文件大小和 SHA256，确认全部复制成功后再启动。
Linux 的 systemd 服务和反向代理配置需要在 Windows 另行配置。

`deploy/windows/` 提供启动与迁移校验脚本，复制到包含 `xm.exe` 的迁移目录根部使用。
`verify.bat` 读取同目录的 `manifest.json`，清单是包含 `path`（相对路径）、
`bytes` 和 `sha256` 的 JSON 数组；清单应在打包时生成，首次启动前运行校验。
校验脚本兼容 Windows PowerShell 5.1 的 JSON 数组返回行为。
若修改了被清单覆盖的脚本，需同时更新对应的大小和哈希，不能沿用旧清单。
空间不足时，可使用 [`deploy/transfer/`](deploy/transfer/README.md) 中的临时下载脚本流式传输已准备好的迁移目录。

Windows 使用原生磁盘空间查询；文件仍在提交前刷新到磁盘，但目录元数据同步遵循
Windows 文件系统行为，不使用 POSIX 目录 `fsync`。

## 快速开始

```bash
cd /home/zyx/XM
go build -o xm ./cmd/xm
./xm serve  # 无需预置配置，首次启动进入设置向导
```

打开 http://127.0.0.1:8080，首次启动显示三步设置向导：

1. **数据库**：选择 SQLite 或 MySQL。MySQL 填写地址、端口、数据库名称、账号、密码；也支持密码环境变量、TLS CA 与证书主机名。点击“测试数据库并继续”会验证建表和事务读写，不保留测试记录。数据库需提前创建。
2. **媒体存储**：选择本地文件系统、WebDAV 或 S3 / S3 兼容服务，填写对应凭据。点击“测试存储并继续”会验证存储读写与清理。WebDAV 根目录和 S3 Bucket 需提前存在。
3. **管理员账号**：设置用户名、密码并确认密码。用户名为 3–32 位字母、数字、下划线、点或短横线（首位不能为点或短横线），区分大小写；密码至少 8 字节，页面要求至少 8 位。 最后点击“完成设置”，将管理员凭据和运行配置统一提交到数据库。

完成后点击“前往登录”，使用刚设置的**用户名和密码**登录，不自动登录。**数据库和存储配置随初始化完成锁定**：不允许直接修改目的地、凭据；可通过「设置 → 数据迁移」受控执行 SQLite3 ↔ MySQL、本地 ↔ S3 / WebDAV，并在迁移时填写新的目标连接。Cookie、代理、监控账号、轮询和通知仍可管理。

**接入已有数据库**：新主机在第一步连接到已初始化的 MySQL 数据库时，向导会自动跳过媒体存储设置，改为验证原管理员用户名和密码。验证通过后只保存新主机的 `config.yaml` 数据库连接信息，沿用原管理员、存储、Cookie、监控、通知及运行设置，不重新初始化、不覆盖原配置，也不向存储写入测试文件。密码错误或配置损坏时不会保存连接；验证每分钟最多尝试 6 次。接入后仍需用原管理员账号登录。

接入前请停止旧主机的 XM 服务；同一数据库不支持多个实例同时运行，工作锁未释放时会拒绝接入。原监控和通知计划将在新主机恢复执行。若使用本地媒体存储，需先把旧主机数据目录中的媒体文件迁移到新主机；数据库中的 Chrome 路径、代理及存储端点也必须在新主机可用。此流程不自动复制本地文件。

登录后，在「设置」导入 Cookie、配置代理，再到「账号」添加目标。已有命令行采集的数据也显示在同一账号列表。向导不迁移已有 SQLite 数据；检测到归档时，禁止直接切换到 MySQL，以免看起来丢失历史内容。

首次打开页面即可设置，无需初始化验证码。数据库或存储测试失败不会创建管理员，可以修正后重试。完成标记随数据库管理员记录持久化，重启不会再次进入向导。只有完整的新版初始化记录才会跳过向导；开发阶段不保留旧版登录和可修改存储的兼容路径。本项目处于开发阶段，不兼容旧版配置、表结构或媒体目录；升级到这版需清空旧数据并重新初始化。正常重启不会清空数据。

管理员用户名、密码盐和哈希，以及初始化锁定状态，保存在数据库 `admin_accounts` 表中，不再生成 `admin.json`。登录会话有效期 12 小时，重启服务需要重新登录。管理员记录或运行配置损坏时服务会报错，需恢复备份，不会自动开放重新注册。

### 管理页面

- **首页**（`#home`）：默认展示已开启首页显示的账号的推文、回复和转推，按发布时间倒序排列，同一推文去重，引用随原推文嵌套展示。支持关键词搜索、媒体筛选、连续加载、图片放大和视频播放；点击作者名称进入其归档。
- **账号**（`#accounts`）：合并原来的推文归档与账号监控，包含监控账号及仅保留归档的账号，每个账号只显示一次；支持按名称、当前／原用户名搜索，按数量或最近采集排序，按启用、暂停、仅归档、需关注、首页显示状态筛选。点击头像或名称进入独立用户页（`#user/用户名`）。用户页采用类似 X 的个人资料头部和单列时间线，支持推文／回复／媒体／收藏切换、关键词与媒体类型筛选。推文栏排除回复，回复栏显示该用户发出的回复，媒体栏包含两者及引用中的媒体。首页与用户页默认每批 24 条，可在「设置 → 界面显示」调整；后续加载使用游标分页，保留已展开文字和视频状态，失败可重试。搜索与媒体筛选同时包含引用推文。
- **滚动预加载**：首页与账号时间线在倒数第 3 条推文接近屏幕时自动加载下一页，并保留距底部 320 像素的触发兜底；每次只发出一个分页请求，不重建已加载的推文。失败后停止自动重试，可点击“重试加载”继续。
- **收藏**：推文与已归档引用右上角提供书签按钮，收藏状态按推文 ID 共享，重复采集不覆盖。主时间线默认进入「全部」，「收藏」展示全部收藏；账号页在「媒体」右侧增加「收藏」，展示该账号归档（含引用）中的收藏。收藏按收藏时间倒序，支持搜索、媒体筛选及滚动分页；取消收藏成功后从收藏列表移除，不删除推文。账号隐藏或移除监控不清除收藏，收藏表随 SQLite3 / MySQL 数据库迁移保留。此功能只保存在 XM 中，不同步到 X。
- **媒体显示**：界面显示中可设置视频默认静音、循环播放（默认关闭）和图片/视频客户端缓存时长。视频点击后才加载，不生成封面；单击画面在全屏与内嵌之间切换且保留播放进度，播放/暂停、静音和进度使用独立控件。图片查看器居中展示原图，不显示左右箭头和关闭按钮，支持手指或鼠标左右拖动切换、向下拖动关闭，也可用方向键切换、Esc 关闭；同一推文内切换不跨账号，滑动时跟手，松开后切换或回弹，遵循系统减少动态效果偏好。
- **显示主题**：在「设置 → 界面显示」选择日间、夜间或跟随系统；夜间使用接近 Twitter「熄灯」模式的纯黑背景、灰白文字和蓝色强调色；登录页、时间线及管理页统一生效，刷新页面会恢复已保存选择，跟随系统时响应系统主题变化。
- **账号列表中的管理操作**：首页显示开关可直接调整；展开“管理”后添加／编辑、暂停／恢复、取消或重新添加监控，展开“采集详情”查看计划、异常与断点；自动采集周期在设置中统一配置，每个账号可选择是否包含回复，以及是否在首页主时间线显示（默认显示）。隐藏仅影响首页「全部」列表及其搜索与筛选，不影响采集、账号归档、引用内容及收藏列表。支持按账号名、推文数量升降序、最近采集时间排序，按采集状态和首页显示状态筛选；详细异常与断点信息可展开查看。支持检查新动态、继续补采历史、重新扫描历史及停止当前任务。重新扫描只清除未完成断点，不删除归档。取消监控保留已归档内容、收藏和首页显示偏好；没有监控的归档账号也可调整首页显示，重新添加改名账号会沿用原归档。列表先加载基本资料、后补统计；运行状态轮询不重复计算历史推文总数。返回列表保留筛选、排序、展开状态和滚动位置。旧 `#archive`、`#monitors` 链接自动转到 `#accounts`。
- **任务**：分别查看当前任务、持久化 FIFO 等待队列和最近 20 次真实执行记录；显示增量采集/历史补采/重新扫描模式、任务来源、队列位置、全局等待原因、读取/新增数量及错误信息；当前任务显示执行阶段、已运行时长、剩余时限和账号媒体归档数量（含引用媒体）；可单独取消尚未开始的排队任务，而不暂停对应监控账号。
- **通知**：先查看渠道和发送记录，新增或编辑时展开表单，支持 Telegram 与通用 Webhook。
- **设置**：按“X 登录 / 采集设置 / 界面显示 / 归档存储 / 数据迁移”分组；配置滚动等待、队列任务间隔、自动采集周期、时间线边界，以及限流冷却、网络超时、媒体大小与重试、浏览器复用等高级参数，导入 Cookie、配置及测试代理，查看锁定的数据库和媒体配置。网络代理、限流冷却恢复和 Chrome 环境诊断位于采集设置下方，代理配置独立保存。“X 登录”只管理采集凭据，监控对象在“账号”页面管理。“界面显示”按外观与时间线、视频播放、浏览器缓存分组；“归档存储”中的缓存是服务器缓存，仅远端存储显示。采集设置按采集计划、时间线采集、浏览器与任务、网络与限流、媒体归档分组，各组默认值仅填入本组，保存后生效。未保存修改在当前页面内保留，切换页面或保存其他表单不会覆盖；刷新或关闭前提示保存，草稿不写入浏览器存储。

手机端提供带文字的底部导航，监控列表自动变为账号卡片，表单、弹窗、图片和视频适配窄屏。

“包含回复”先读取回复时间线，再读取普通推文时间线。两页按推文 ID 去重，共用自动监控的内部安全上限；回复已达到安全上限时不再追加普通推文。兼容 `UserTweetsAndReplies` 与 `UserRepliesTimeline`，不会展开抓取其他人对这些推文的全部评论。两条时间线共享单次任务时间上限。修改“包含回复”会重新建立对应采集范围的历史基线，已归档内容保留。

监控在首次成功读取资料时绑定 X 用户 ID；之后会核对身份，并以 ID 筛选推文作者。已有归档可从唯一的历史作者 ID 恢复绑定；出现多个 ID 时暂停，避免误判。改名时先尝试最后确认的用户名，失败后通过已归档推文的固定 ID 查找作者当前主页，再核对 ID。监控列表和用户页显示新用户名，历史推文、媒体、轮询计划与通知去重记录沿用原档案，页面链接保持稳定。已配置异常通知的渠道会收到改名或身份校验失败提醒。

此方式仍依赖 Cookie 的查看权限：若没有可用历史推文、参考推文被删除、锁推权限已撤销，且 X 按用户 ID 查询也不可用，程序会暂停并提示，不会自动改绑到旧用户名的新持有者。首次成功绑定之前，无法判断一个用户名过去属于谁。内部归档键保留创建时的用户名；添加已识别的新用户名会提示已有监控，不会重新建立档案。

自动采集使用单个串行 worker 和数据库持久化 FIFO 任务队列：同一账号不会重复入队，自动任务、手动任务与失败重试共用队列；手动请求命中已有自动任务时升级该任务，不产生重复采集，也不绕过全局冷却。首次添加账号默认执行历史补采；只有历史基线已完成，或 X 未提供可靠结束标记而被标为“可见历史范围不确定”后，周期任务才使用增量模式。历史补采和重新扫描不会因为连续遇到已归档推文而提前停止。周期到达不会叠加另一份未完成批次；限流或服务重启后继续未完成的账号，重试任务移到其余已排队任务之后，已完成账号不重复采集。每个账号任务的时限统一使用“浏览器最长复用时间”，默认 6 小时，可在设置中调整为 1～24 小时；旧版独立任务时限不再生效，浏览器采集、头像处理和媒体下载/上传共用这一时间预算。常规采集不再使用条数、页数或滚动次数限制，仅保留极高的内部故障防护上限；达到时间上限时，正文、分页断点和未完成媒体任务保留，后续任务继续。任务超时记为未完成，不记为用户取消。可为相邻账号任务配置 0～3600 秒间隔，修改后会调整下一账号启动前尚未结束的等待。整个批次完成后统一计算下一次时间。自动采集周期以小时设置，默认及最低 1 小时；保存新周期会立即把已启用账号的下次计划改为当前时间加新周期，但不会撤销已排队或正在运行的当前批次。配置和下次计划在同一事务中保存，提交成功后才更新内存配置；写入失败时一并回滚，可重试保存。

浏览器在首次实际采集时启动，跨自动周期和手动任务复用。每个账号使用独立的任务标签页，任务结束或取消后关闭该页，空闲时保留空白根标签页。每次任务前通过本地 Chrome 协议检查健康状态，不访问 X；Cookie、代理或浏览器采集参数变更时在任务边界重建实例。异常退出或失去连接会保留任务和断点，启动/连接连续失败按 30 秒起、最长 5 分钟退避；重建不清空 X 限流冷却。为限制长期资源累积，实例默认达到 6 小时或 100 次任务后，在下一任务开始前重建（可在采集设置中调整）；服务关闭时清理 Chrome、临时配置目录和代理桥接。

账号分别记录结果；无权访问只暂停对应账号，普通失败不会阻止后续账号，Cookie 失效或 X 限流则中止当前执行片段并保留剩余队列。限流会让全部采集（含手动任务）冷却：首次至少等待 15 分钟或统一轮询周期中的较长者，连续限流逐次翻倍，常规上限 6 小时；轮询周期超过 6 小时时仍遵守该周期。如果 X 返回更晚的 `Retry-After` 或 `x-rate-limit-reset`，则等待到该时间后再留 5 秒余量。限流次数和重试时间持久化，整批自动采集无采集错误后才重置退避；补完曾失败批次的尾部、单个账号成功或重启不会缩短等待。限流及其他采集错误保留追赶位置，不再增加下次翻页上限。页面显示最早重试时间，并不保证届时 X 已解除限制。全局暂停在当前账号结束后生效，剩余自动任务保留，手动采集仍可用（仍受限流冷却约束）。Cookie、代理和账号编辑从下一个任务生效。服务重启会恢复监控计划，并标记被中断的任务。

采集请求完全由 X 页面导航和滚动自然触发，XM 不拦截、排队或按固定频率放行浏览器请求。每次滚动后会等待这一轮 GraphQL 网络活动结束，再按「滚动基础等待 ± 随机浮动」决定下一次滚动；默认随机等待 15～25 秒。只有 X 实际返回 429 时才触发全局限流冷却。

限流冷却可选保守（至少 30 分钟、上限基准 12 小时）、均衡（至少 15 分钟、上限基准 6 小时）或快速（至少 5 分钟、上限基准 2 小时）；统一轮询周期及 X 返回的更晚重置时间仍然优先。较短冷却会增加再次限流或触发验证的风险。

设置 → 采集设置 → 限流与恢复提供“清除采集冷却”按钮：清除收到 429 后建立的本地冷却和连续限流计数，并让启用的监控重新具备运行条件；暂停设置、排队任务、归档与分页断点保留。正在运行的批次结束或停止后才能重置。这不会解除 X 服务器端的限制，重试仍可能再次限流。

页面保存的代理、统一轮询周期、暂停状态、采集参数、存储配置和通知渠道统一保存在所选数据库的 `system_settings`、`storage_profiles`、`notification_channels` 表；Cookie 在 `x_cookies` 表，监控列表和任务状态也在数据库中。Cookie 或代理更新在下一个任务生效，统一周期及高级采集参数作用于全部启用账号。代理测试只验证网络响应，不验证 Cookie 或锁推访问权限。

`serve`、`collect`、`retry-media`、`import-cookie` 对同一数据目录互斥。服务运行期间请通过页面导入 Cookie 和采集；使用命令行采集/修复前先停止服务。`list`、`status` 可同时读取。

### 服务器部署

默认仅监听本机。当前仓库附带的 systemd 单元固定监听 `127.0.0.1:9980`；可通过 SSH 转发访问，或放在 HTTPS 反向代理后面：

```bash
./xm serve -config /absolute/path/config.yaml -listen 127.0.0.1:9980 -secure-cookie
```

`-secure-cookie` 用于浏览器通过 HTTPS 访问的部署；普通本地 HTTP 访问不加此参数。反向代理须保留原始 `Host` 和 `Origin`，把整个站点根路径转发给 XM。首次设置尚未完成时，服务只允许绑定回环地址，避免远程访问者抢先创建管理员；完成初始化后才可按需监听其他接口。远程访问应使用 HTTPS 或 SSH 隧道保护 Cookie、密码和私密内容。停止时使用 SIGTERM / Ctrl+C，以便取消采集并保留已保存结果。

用户级 systemd 安装示例：

```bash
mkdir -p ~/.config/systemd/user
cp deploy/xm.service ~/.config/systemd/user/xm.service
systemctl --user daemon-reload
systemctl --user enable --now xm.service
curl --fail http://127.0.0.1:9980/healthz
```

单元使用 `Restart=on-failure` 自动恢复异常退出，配置和数据文件以 `UMask=0077` 创建。若需要注销桌面会话后仍运行，可由管理员为该用户启用 linger。

仓库不提供预置配置或示例配置文件。全新部署直接运行 `./xm serve`，首次设置完成后自动生成本机 `config.yaml`（已被 Git 忽略）；设置完成前不会生成此文件。它只保留启动所需的数据库连接信息和本地数据目录，生成结果如下：

```yaml
data_dir: ./data
database:
  driver: sqlite
```

MySQL 连接参数通过首次设置页面生成，数据库密码可以通过 `password_env` 引用环境变量。数据库连接信息必须留在启动配置中，程序才能读到数据库内的其余配置。`data_dir` 相对配置文件定位，用于 SQLite、本地媒体、远程上传暂存和进程锁；读取后转换为绝对路径。启动配置含 MySQL 密码时权限为 `0600`。

代理在管理页面的「设置 → 采集设置 → 网络代理」配置，支持 `http://`、`https://`、`socks5://`、`socks5h://`，必须填写端口，可包含代理用户名和密码。留空明确直连，不继承 `HTTP_PROXY` 等环境变量。采集参数使用内置推荐值并在初始化时入库，可在管理页面的「设置 → 采集设置」调整，不能把运行参数添加到启动文件。数据库和存储仍不能在初始化后的管理页面修改。

请求超时默认 60 秒；单媒体默认上限 512 MiB。Chrome 默认最多复用 6 小时或 100 个任务，任一边界到达后重建。媒体临时失败默认从 5 分钟开始指数退避，最长 24 小时；可配置最长 7 天。永久格式、域名或大小错误不会自动重试，S3 单文件仍受 5 GiB 上限约束。

### 导入 Cookie

在你已登录 X 的浏览器中，从开发者工具的 Application / Storage → Cookies → `https://x.com` 读取 `auth_token` 和 `ct0`，在本地编辑器里保存为 `cookies.json`：

```json
{
  "auth_token": "替换为你的实际值",
  "ct0": "替换为你的实际值"
}
```

```bash
chmod 600 cookies.json
./xm import-cookie -file cookies.json
```

也支持 `auth_token=...; ct0=...` 格式的 Cookie 请求头、浏览器导出的 JSON 数组，以及 Netscape Cookie 文件。只保留 `auth_token` 和 `ct0`，忽略其他 Cookie。使用 `-file -` 可从标准输入导入。

也可在「设置 → X 登录 → 从 API 获取 Cookie」保存 GET 接口地址、可选 Bearer Token 和代理选项，点击「保存并获取 Cookie」。接口返回上述 JSON 对象或 Cookie 数组；响应上限 1 MiB，超时 15 秒，不跟随重定向。`cookie_sources` 表持久化接口配置与 Token（明文），不写入配置文件，Token 不下发到页面。地址变更会清除旧 Token，需重新填写。

启用自动恢复后，服务采集明确检测到登录失效时会请求 API 一次，保存新 Cookie 并用新的浏览器会话重试失败账号。自动恢复次数持久化，重启不会重置限制；API 请求失败或新 Cookie 再次失效时停止，保留现有归档，页面显示状态，需手动获取或导入。一次成功的登录采集或手动导入后才允许下一轮自动恢复。网络异常、账号访问权限不足和限流不会触发 Cookie 自动获取。此功能由 Web 服务调度器执行，独立 CLI 采集仍使用最近保存的 Cookie。

不要把 Cookie 粘贴到聊天、命令行参数或提交到 Git。导入成功仅代表格式检查通过，不代表登录态在线有效。导入文件仍由你自己保管或移除；程序不会擅自删除它。

### 验证公开与锁推账号

先分别采集少量内容，将下面的占位用户名替换为真实目标：

```bash
./xm collect -users public_user -limit 10
./xm collect -users approved_private_user -limit 10
```

正常后可以指定多个目标：

```bash
./xm collect -users public_user,approved_private_user -limit 100
./xm collect -users approved_private_user -limit 100 -replies
./xm collect -users public_user -limit 500 -backfill
./xm list -user approved_private_user -limit 20
./xm status
```

`-limit` 是**每个目标**本次最多读取的推文数（1～10000），不是历史完整性保证。默认使用增量模式：仍从顶部读取最新动态，但连续遇到已归档边界后停止继续翻旧页。`-backfill` 禁用这个增量边界，按本轮上限继续向历史滚动；它不依赖或持久化 X 的易失分页游标。`-replies` 打开推文与回复页面，但只归档目标账号本人发出的内容，不把对话模块中的其他人回复当作该账号的推文。

浏览器使用新的临时配置目录，导入 Cookie 后要求检测到已登录界面；不会主动退回访客模式。采集依赖页面实际返回的数据，不硬编码 GraphQL query ID，不读取你的日常浏览器配置。浏览器退出后清理临时配置；异常断电或强制杀进程可能留下临时目录。

每批推文和媒体任务先在同一个数据库事务内提交，再进入媒体下载阶段。重复采集不会重复插入；内容未变化时只更新 `last_seen`，不重写正文和媒体索引，也不重复下载已经成功的媒体。

后台把任务明确分为三种模式：`incremental` 从最新动态向下读取，连续遇到存量数据后停止；`backfill` 从最新内容开始或从分页断点继续，忽略存量边界并尽量向历史深处读取；`rescan` 清除未完成断点后重新扫描当前可见历史，但保留所有已归档内容。首次账号默认进入 `backfill`。未完成的补采分别保存回复和普通推文的分页断点。每页推文、下一页游标、X 明确返回的时间线结束标记和读取/新增计数在同一事务中提交；限流、达到单次任务最大时间或重启后，使用当前 X 页面生成的请求从已提交断点继续，已完成的回复阶段不会重新读取。Web 自动和手动任务不再设置条数、页数或滚动次数限制；分页游标无法应用或失效时暂停该账号，页面提供“重置断点并重试”，重置保留旧追赶锚点与归档，也不会跳过全局限流冷却。

历史断点处理完成后，同一个队列任务自动切换为增量模式，从顶部检查补采期间的新动态，直到到达该次补采开始时记录的普通推文/回复边界。该收尾步骤保留任务来源和断点边界；手动任务即使关闭了自动采集，也会完成收尾，不会重新扫描全部历史，仍遵守账号间隔与限流冷却。升级前未记录分页游标的未完成任务需要先从顶部建立一次断点。采集记录分别显示读取与新增条数；旧记录未保存新增统计的显示“新增未记录”，不推算为零。

自动监控按当前响应中的推文 ID 分批查询该账号的完整归档，不再仅查看最近 4000 条；旧推文不会重复占用新增条数额度，深度补采可以继续向前推进。正常增量轮询默认在连续 3 条已归档动态处提前停止；历史补采与重新扫描忽略该边界，直到 X 明确返回时间线结束、达到安全上限或本次不再观察到时间线进展。只有 X 的分页响应明确给出结束标记时才显示“当前可见历史已完成”；仅滚到稳定页面底部会显示“可见历史范围不确定”。这里的完成只表示当前账号、当前权限下 X 可见的历史，不保证包含已删除、受限或平台未返回的内容。

停止原因：

- `limit_reached`：命令行采集达到显式 `-limit`，或命中仅用于故障防护的内部极高上限。
- `max_scrolls_reached` / `page_budget_reached`：旧版本任务记录可能保留的兼容状态；新任务不以此作为常规边界。
- `known_boundary_reached`：增量轮询已连续遇到已归档动态，或追赶模式已到达原先保存的锚点，不再重复翻取更旧页面。
- `no_new_posts_observed`：已滚到页面底部，连续多轮页面高度、位置和时间线响应均无进展；不能据此认定已取得全部历史。

`Protected` 为 `null` 表示本次未读取到目标资料，不能推断为公开账号。无法访问、登录失效、限流或响应结构变化均返回非零退出码。只出现无法访问的占位内容也会报错，不计为成功的空时间线。

### 媒体重试与修复

```bash
./xm retry-media
./xm retry-media -user approved_private_user
./xm retry-media -verify
```

图片请求原图；视频和动图选择响应里最高码率的 MP4。当前不合成 HLS；没有 MP4 的媒体会记录失败原因。会一并归档时间线响应中包含的引用推文正文、图片、视频，最多保留 4 层引用。引用与原推文保持关联，在用户页显示为嵌套卡片，不作为该用户自己发布的推文重复列出；引用条数不计入每轮目标推文上限。引用中的媒体使用同一下载、去重和重试机制，`retry-media -user 用户名` 也覆盖这些媒体。不会主动请求未返回的引用内容或外部链接附件；被删除、无访问权限或源站未提供的引用显示为不可用。媒体地址可能过期，必要时先重新采集刷新地址，再重试。媒体等待重试或永久失败时，任务不会被报告为媒体已恢复；只有对应账号及其引用内容的媒体全部归档成功后才发送恢复通知。

采集时将引用正文、引用关系和媒体任务与原推文一起写入同一事务。仅引用保存的作者不会自动加入首页用户列表。页面推文计数以目标账号的时间线为准，数据库 `posts` / CLI `status` 的总数还包含引用记录。

下载使用同一代理，不向媒体 CDN 发送账号 Cookie。只接受 `pbs.twimg.com` 和 `video.twimg.com` 的 HTTPS 地址，重定向也受相同限制。流式下载到私有临时文件，检查大小和响应类型，成功后原子替换；数据库保存 SHA-256。临时网络或存储失败采用 5 分钟起、最长 24 小时的指数退避；不支持的 HLS、非法来源、类型不符和超过上限的文件标记为永久失败，避免每轮重复请求。源地址发生变化时会重置该媒体的失败状态。`retry-media -verify` 可人工重新检查全部记录。

## 数据库：SQLite / MySQL

默认使用 SQLite。MySQL 模式把正文、引用关系、媒体索引、监控计划、运行记录和通知队列保存到远程数据库；图片与视频仍使用配置的本地、WebDAV 或 S3 存储。支持标准 MySQL 协议，已使用 MySQL Community 8.4 验证；建议使用 MySQL 8.4。

### 配置 MySQL

1. 准备专用于 XM 的空 MySQL 数据库，以及能访问该库的账号。XM 自动创建表，不自动创建数据库或云资源。账号需要该库的 SELECT、INSERT、UPDATE、DELETE、CREATE、ALTER、INDEX、REFERENCES 权限；运行时还使用 MySQL 命名锁，避免多个 XM 写入进程同时使用同一数据库。
2. 确保 XM 主机可以连接数据库端点和端口（默认 3306）。私网端点需要部署在可达的 VCN / VPC、VPN 或通过隧道连接。管理页里的 HTTP/SOCKS 代理只作用于 X、媒体和通知，**不会代理 MySQL TCP 连接**。
3. 在初始化页面填写 MySQL 信息，程序会生成下面的 YAML `database` 部分，保留原有 `data_dir`；媒体存储与通知配置随数据库迁移。不要直接改数据库类型来迁移数据；返回本地 SQLite 可使用下面的设置页迁移功能。

```yaml
database:
  driver: mysql
  host: your-mysql-host
  port: 3306
  name: xm
  user: xm_app
  password_env: XM_MYSQL_PASSWORD
  tls_mode: verify_identity
```

`password_env` 指定密码环境变量名，优先于可选的 `password` 字段；指定但未设置时直接报错。可在本机终端用 `read -rs XM_MYSQL_PASSWORD; export XM_MYSQL_PASSWORD` 输入，不把密码写入命令历史。systemd 启动时需给服务单独配置 EnvironmentFile（权限 0600），终端中的 export 不会自动传给 systemd 服务。若直接填写 `password`，保持配置文件权限 0600，不要提交到 Git。

连接默认要求 TLS 1.2+ 并验证证书与主机名，使用系统可信 CA。私有 CA 可通过 `ca_file` 指定 PEM 文件，相对路径以配置文件目录为基准；`server_name` 可用于通过隧道连接时验证实际数据库证书的主机名。可显式设置 `tls_mode: disabled` 禁用 TLS，本机和远程地址均支持；连接将不加密，请仅在可信网络或已加密隧道中使用。获取证书时应使用数据库服务提供的可信来源。管理 API 不回显数据库密码。

MySQL 使用 utf8mb4，支持中文和 emoji；采用严格 SQL 模式，超长或无效字段报错而非静默截断。一个 MySQL 数据库仅供一个 XM 实例及一个 X 登录账号使用；命名锁连接丢失时停止服务，需恢复网络后重启。数据库高可用切换可能中断在途任务，重启后恢复调度；尚未实现多实例集群调度。

### 设置页数据迁移：数据库与存储

入口为「设置 → 数据迁移」，分为独立的**数据库迁移**和**存储迁移**两个部分。页面根据当前数据库、默认存储和已有连接提供方向与目标。检查操作不改动数据库、存储或启动配置；MySQL 检查会连接目标确认空库，但不建表。只有输入 **开始迁移** 并确认后才启动任务，一次只执行一个任务。

- **MySQL → SQLite**：预估空间，等待当前采集/通知结束并阻止新写入；从一致性快照复制全部业务表，验证行数、逐行内容 SHA256、外键、SQLite 完整性、管理员凭据及运行配置。默认创建 `xm.db`；若该文件或其 WAL/SHM 已存在，则创建独立的 `xm-migrated-<id>.db`，不覆盖已有文件；`database.sqlite_file` 指向新文件。原启动配置备份在 `data_dir/migration-db-*/bootstrap-before.yaml`，权限 0600。校验通过后切换启动配置并受控重启，需重新登录。源 MySQL 不删除、不双写。
- **SQLite3 → MySQL**：填写空 MySQL 数据库连接，支持密码环境变量及 TLS 证书设置。维护期间暂停写入，获取目标数据库工作锁后建表、事务复制并逐表校验，验证管理员与运行配置后切换启动配置并自动重启。源 SQLite 保留。目标非空、被其他 XM 实例占用、存在非 XM 表或非 InnoDB 表时拒绝迁移。重试需重新提供连接凭据；若提交成功但切换失败，目标已非空，需要检查该副本或使用新的空库，不能直接覆盖。
- **Samba / S3 / WebDAV → 本地**：等待当前任务结束后将新增媒体改存本地，再后台搬迁所选远端的已归档媒体，复用正常下载的 `media/users/作者目录/` 路径规则和已记录的作者目录名。逐文件校验大小、SHA256、落盘同步和回读，成功后才更新媒体索引；原媒体访问地址不变。源对象和连接配置保留。失败项仍由远端提供；缺少可信大小/哈希的文件不会跳过校验。缓存不代替迁移。
- **本地 → Samba / S3 / WebDAV**：选择已有远端连接，或在当前默认存储为本地时填写新的连接。任务开始后先验证目标读写权限，通过后切换新增媒体的保存位置；历史本地文件保留 `media/users/作者目录/文件名` 作为远端路径（再加配置的目录前缀），旧布局文件按原作者生成该路径；上传并回读校验成功后才更新引用。本地源文件保留；失败文件继续从本地读取，重试可复用已上传并验证的副本。连接测试使用随机 `.xm-check/` 文件，完成后删除测试文件。
- **Samba 原生连接**：首次设置或存储迁移中选择 Samba (SMB)，填写 `smb://服务器[:端口]/共享名`（默认 TCP 445）、用户名、密码和可选目录前缀。域账号填 `域名\用户名`。共享必须已存在且可读写；使用 SMB2/3、NTLMv2 身份认证和消息签名，不需要系统挂载，不使用 HTTP/SOCKS 代理。数据库与启动配置仍在本机；媒体迁移不修改数据库位置。连接前请确保 XM 主机可达共享端口。
- **清理本地副本**：本版起，本地迁往远端时会在更新媒体索引的同一事务中记录保留的源文件。「迁移后的本地副本 → 检查本地副本清理」展示数量和容量，输入 `清理本地副本` 后执行独立任务。清理期间暂停写入；每个文件重新验证当前远端引用、远端大小与 SHA256、本地内容和无在用引用后才删除。远端无法访问、内容变化、路径异常或仍被引用时保留该文件并展示失败原因；支持暂停和重试。只处理记录中的媒体副本，不扫描删除旧文件，不删除数据库、远端对象或在用本地媒体。早期版本未记录的迁移副本不会自动纳入清理；“确认完成并隐藏”仍仅隐藏进度。
- 进度包含阶段、数量、媒体容量和失败明细（最多 100 条）。支持暂停和手动继续；服务中断后标记暂停，不自动发起迁移。存储重试仅处理仍在来源存储的文件，暂停后默认存储保持在已切换的目标；数据库重试从新的完整快照开始。
- 迁移成功后点击“确认完成并隐藏”，进度卡片不再显示，刷新页面或重启服务后仍保持隐藏；新的迁移会重新显示进度。确认只记录已阅状态，不删除迁移记录、归档或源文件；进行中、暂停和失败任务不能隐藏。
- 本地指服务器磁盘。空间检查是估算，不是配额；远端容量需自行确认，传输和回读可能产生请求/流量费用。切换后的新数据不再同步到源数据库，不能直接切回旧库声称无损回退。
- 日志在 `data_dir/migration-state.json`；数据库暂存目录与失败副本保留以便排错，不自动清理。验收后如需清理，应停服确认当前 `database.sqlite_file` 与备份路径。迁移不提供自动删除远程数据功能。

### 命令行迁移：同版本 SQLite 到 MySQL

此命令只支持当前版本的表结构，不包含旧版本升级兼容。迁移不是切换配置后自动发生的；已有归档请按以下顺序操作：

1. 停止正在使用该数据目录的全部 XM 进程。备份原配置和整个 `data_dir`（包含 SQLite 和本地媒体），另行备份远程对象。
2. 复制**现有配置**为 `config.mysql.yaml`，增加上述 MySQL 配置，继续使用原 `data_dir`。目标库的 XM 表必须为空。先不要启动 MySQL 模式的管理服务。
3. 设置密码环境变量，执行：

```bash
./xm migrate-mysql -config config.mysql.yaml -source /absolute/path/data/xm.db
./xm status -config config.mysql.yaml
./xm serve -config config.mysql.yaml -listen 127.0.0.1:9980
```

迁移只读源 SQLite，逐表导入并保留推文 ID、引用、媒体存储连接和路径、监控状态及通知队列。全部目标数据在一个事务中提交；失败回滚，非空目标拒绝覆盖。建表操作不属于数据事务，失败时可能留下空表。提交结果因网络中断而无法确认时，先检查目标数据，不要直接重试。大归档迁移需要足够的数据库空间、事务日志容量和维护时间。

Cookie、管理员凭据、存储与通知配置会随数据库一起迁移，不会搬运媒体文件；因此应保留原媒体目录和最小启动配置。暂停轮询后迁移可便于先核对归档，但通知队列会在启动管理服务后继续发送。保留原 SQLite 作为迁移前备份；切回 SQLite 不会自动同步后来写入 MySQL 的数据。迁移验收后，可让原 systemd 服务加载新配置和密码环境，避免同时启动两个实例。

MySQL 模式的备份需包含数据库一致性备份/云快照、本机数据目录与配置，以及远程媒体对象。单独备份本机目录不能备份远程正文数据。

## 媒体存储：本地、WebDAV、S3

媒体存储在首次设置向导中配置并测试。完成后，管理页 **设置 → 归档存储** 显示受保护的配置，不能直接新增、编辑或切换；通过 **设置 → 数据迁移 → 存储迁移** 可在本地和 S3 / WebDAV 之间迁移，也可在本地迁出时添加目标连接。默认本地存储无需额外凭据。远程连接测试在前缀下的 `.xm-check/` 创建随机小文件，验证写入、HEAD、读取和删除；成功后删除测试文件，WebDAV 可能保留空测试目录。

| 类型 | 配置与要求 |
|---|---|
| 本地磁盘 | 保存到 `data_dir/media/`，无需远程账号 |
| WebDAV | 填写**已经存在的最终根目录 URL**，例如 `https://nas.example.com/remote.php/dav/files/user`，以及用户名、密码或应用密码。需要 PUT、GET、HEAD、MKCOL 权限；连接测试还需要 DELETE 权限。子目录自动创建，不跟随重定向 |
| Samba (SMB2/3) | 填写 `smb://主机[:端口]/共享名`、用户名和密码，可指定共享内目录前缀；无需挂载。数据库保留在本机。支持媒体上传、下载、视频范围读取、双向迁移和校验后的本地副本清理 |
| S3 / 兼容服务 | 填写 Bucket、Region、Access Key、Secret Key；可选 Session Token。Bucket 需提前存在。AWS S3 可留空 Endpoint，MinIO 等填写服务 Endpoint 并按服务要求勾选 Path-style。需要 GetObject、PutObject，测试还需要 DeleteObject；不要求公开 Bucket。单文件上传上限 5 GiB，不支持分片上传 |

目录前缀可填 `xm-archive`，文件会保存为 `xm-archive/media/users/alice_123456/哈希.扩展名`。请为此归档使用独立前缀，避免其他程序覆盖文件。远程请求默认直连；勾选“远程存储使用代理”后，使用与 X 相同的代理。请求超时单独配置，默认 120 秒；较大的视频或较慢的连接可提高。支持 HTTPS 和显式配置的 HTTP（例如局域网设备），HTTPS 证书必须有效。

媒体统一按作者保存到 `media/users/<首次保存时的用户名>_<X 用户 ID>/`。例如 `media/users/alice_123456/`，目录映射在 `media_directories` 表持久保存；同一账号改名后继续使用原目录，同名的新账号使用不同目录。引用推文的图片和视频归到引用作者目录；作者 ID 缺失时使用安全的回退标识。文件名使用推文 ID 与媒体 ID 的哈希，避免重名。本地、WebDAV 和 S3 使用相同目录层级，远程存储可再加配置的前缀。

每个已保存文件在数据库中记录存储连接 ID 和对象路径。本地文件与远程文件可在同一时间线浏览；不要手动删除仍有文件引用的连接。

远程媒体先下载到本机暂存，计算 SHA-256，再上传并用 HEAD 检查大小；数据库确认完成后删除暂存文件。上传失败会记录失败并保留有效暂存文件，重试可复用；不会静默改为本地成功。需要本机留出单个媒体的暂存空间。下载过程不向 X 的 CDN 或远程存储交叉发送账号 Cookie、存储密码。

管理页面通过已登录的 `/media/…` 接口流式读取远程文件，支持视频 Range 和拖动，不向浏览器下发远程密钥或公开链接。读取会经过 XM 主机，消耗主机及存储流量。WebDAV 若忽略 Range，拖动可能需要从头读取并跳过前面的字节。远程存储不可用时该媒体暂不可读。

`retry-media -verify` 会对本地与远程媒体读取并校验完整 SHA-256，远程文件也会产生下载流量；丢失或损坏时尝试从 X 重新下载到原存储连接。连接或权限故障保留已有完成记录并报告校验失败。普通失败重试使用当时选中的存储连接。

远程存储配置与密码、密钥保存在数据库 `storage_profiles` 中，管理 API 不回显秘密值。备份应包含数据库、最小启动配置和媒体对象；仅备份数据库不能恢复媒体。

## 通知：Telegram 与通用 Webhook

管理页面左侧打开 **通知设置**，添加渠道后选择“新动态通知”“异常与恢复通知”，并启用自动通知。可配置多个渠道，每个渠道独立选择事件及是否使用设置中的代理。

### Telegram

1. 在 Telegram 联系官方 `@BotFather`，通过 `/newbot` 创建机器人，获取 Bot Token。
2. 在 Telegram 向机器人发送 `/start`。填写接收会话的 Chat ID；群组 ID 通常为负数，公开频道也可使用 `@频道名`。可以通过 Telegram Bot API 的 `getUpdates` 查看收到的消息中的 `message.chat.id`；如果机器人已配置其他 Webhook，不能同时使用 `getUpdates`，请从现有机器人服务获取 Chat ID。
3. 群组或频道需要先添加机器人并授予发送消息的权限。发送到群组话题时填写 Topic ID；普通会话留空。
4. 填写 Bot Token、Chat ID，保存渠道，再点击“发送测试消息”。测试即使在渠道停用时也会发送；“已加入队列”仅表示排队，需在“最近发送记录”确认“已发送”，并在接收端确认。

Telegram 使用官方 HTTPS Bot API，不支持自定义网关。中国网络下通常需要勾选“使用设置中的代理”，并先在设置中保存可用代理。Token 不回显，编辑时留空保留。[Telegram Bot API](https://core.telegram.org/bots/api#sendmessage)

### 事件与发送规则

- 新动态：每个账号每轮合并一条，包含新增归档条数。首次历史采集默认静默；已归档内容不会因重复轮询再次通知。引用内容随原推文保存，不另计为该账号的新动态。
- Cookie 失效或登录受限：立即提醒，采集暂停。即使在失效后才新增或启用渠道，也会提醒当前登录问题。
- 访问权限丢失：立即提醒，该账号监控暂停；可能是权限变化或账号不可用，不会假定一定是取消关注。
- X 限流：提醒进入冷却期。
- 媒体下载或上传失败：提醒检查下载与存储连接。
- 普通采集错误：连续失败达到 3 次后提醒。
- 恢复：异常后成功采集并完成媒体处理时提醒。同类持续异常在 6 小时内合并，不随每轮重复发送；停止任务不会产生失败提醒。

通知只包含账号、条数和状态，不发送推文正文、图片、视频、Cookie 或原始错误响应。新动态通知可能早于全部媒体成功保存；正文已入库时仍会报告新增归档，媒体失败会单独提醒。

通知通过所选数据库中的队列持久化，由独立 worker 发送，不阻塞采集。临时故障采用退避重试，最多自动尝试 5 次；Telegram 429 会按服务要求延迟。凭据或权限等明确错误直接记录失败，可修正后再次发送测试。页面支持手动重试失败记录，显示最近 30 条；数据库保留最近约 1000 条已完成记录以及全部待发送任务。

发送采用至少一次语义：收件服务已接收、但网络响应丢失或服务在记录结果前退出时，重试可能产生重复消息。更换接收地址、Chat ID、Token 等会取消原配置的待发消息，避免发给新收件方；停用或移除渠道会取消待发的自动通知，已在途请求可能送达。通知仅在 `serve` 管理服务中运行，单次 CLI `collect` 不发送通知。

### 通用 Webhook

向配置 URL POST JSON，例如：

```json
{"id":"唯一事件ID","type":"new_posts","target":"alice","title":"XM · @alice 有新动态","message":"本轮新增归档 2 条动态，请登录 XM 查看正文和媒体。","count":2,"created_at":1792230000}
```

事件类型包括 `new_posts`、`auth`、`access`、`rate`、`collection_failed`、`media_failed`、`recovered`、`test`。HTTP 2xx 表示成功；可选 `Authorization: Bearer …`，`X-XM-Event-ID` 可供接收端去重。禁止跟随重定向；此接口不是企业微信或飞书机器人的专用格式。

通知 Token、完整 Webhook URL 及认证信息保存在数据库 `notification_channels` 中，管理 API 不回显；发送记录只保存事件元数据与经过处理的错误信息。实际 Telegram 可达性及会话权限需要使用自己的机器人发送测试消息确认；自动测试使用模拟传输和本机接收端，不联系真实机器人。

表结构、字段分工和引用关系见 [数据库结构说明](docs/database.md)。

## 数据与隐私

```text
data/
  xm.db                SQLite 默认归档数据库；MySQL 模式不使用此文件
  xm.db-wal            运行期间可能存在的 WAL
  xm.db-shm            运行期间可能存在的共享内存文件
  worker.lock          防止多个采集进程同时运行的系统锁
  media/users/
    alice_123456/      同一作者的图片、视频及远程上传暂存文件（0600）
      哈希.jpg
      哈希.mp4
```

数据目录权限为 `0700`。X Cookie 的 `auth_token` 和 `ct0` 明文保存在当前配置数据库的 `x_cookies` 表中（固定 `id=1`），不做应用层加密，不再使用 `cookies.enc` 或 `cookie.key`。管理页面、后台任务和 CLI 共用此记录，导入时覆盖更新；管理 API 不回显 Cookie。应用不会对数据库正文、原始推文 JSON 和媒体做额外内容加密；如有需要，应使用磁盘加密。

管理 API、推文数据和媒体接口均要求管理员登录；静态登录页面不包含归档内容。媒体支持 Range 请求，不直接暴露数据目录。不要把 `data/` 放在公开 Web 根目录或公开共享盘。`list` 会将正文输出到当前终端，应注意终端日志与重定向文件的访问权限。

存储和通知表中的运行凭据与 `x_cookies` 一样不做应用层加密；管理员登录密码仍只保存加盐哈希。内存会话、浏览器临时目录和上传暂存文件属于运行时数据，媒体文件仍存放在本地、WebDAV 或 S3。

一个归档数据库对应一个 X 登录账号。更新同一账号的 Cookie 可重复运行导入命令；切换到另一个 X 账号时使用独立配置、数据库和 `data_dir`，避免混淆内容的授权来源。尚未实现源站删除、编辑历史和关注权限变化的后台同步，不能作为永久保留源站删除内容的承诺。

备份建议先停止全部 XM 进程，再复制整个数据目录；MySQL 模式还需备份数据库，Cookie 包含在数据库备份中。运行中不要只复制主 SQLite 文件而遗漏 WAL。

## 代理实现

浏览器通过临时的 loopback HTTP 代理桥连接配置的上游代理，以支持带认证的 HTTP(S)/SOCKS5。HTTPS 使用 CONNECT 隧道，没有 TLS 解密。媒体下载直接使用配置的上游代理；代理失败不会切换直连。SOCKS5 连接将目标域名交给代理处理。

Docker 中的 `127.0.0.1` 指容器自身；宿主机代理需使用容器可达的地址。当前未提供 Docker 镜像。

## 故障排查

| 现象 | 处理 |
|---|---|
| 无法启动 Chrome | 安装 Chrome/Chromium，设置 `chrome_path`，检查运行用户权限与沙箱 |
| Chrome 报 SUID sandbox helper 权限错误，但文件已是 root:root / 4755 | 检查用户级 systemd 的 `PrivateTmp`：它可能创建用户命名空间，使 Chrome 看到文件所有者为 65534。使用仓库单元的 `PrivateTmp=false` 与 `RuntimeDirectory=xm-tmp`（0700），保留 `NoNewPrivileges=true` 和 Chrome 沙箱；重新加载单元并重启服务 |
| 未检测到已登录界面 | 浏览器确认登录，重新导入两个 Cookie；有图形环境时设 `headless=false` 查看页面 |
| 无权查看锁推 | 确认提供 Cookie 的账号已被批准关注，且未被移除或拉黑 |
| HTTP 429 / code 88 | 等待限流恢复，减少采集量；程序不自动换账号或高频重试 |
| 未收到时间线 / 响应结构变化 | 检查网络与 X 页面是否正常；持续出现则需要适配解析器 |
| 媒体失败 | 查询 `media.last_error`，检查大小/超时上限和代理，再运行 `retry-media` |
| 崩溃后 runs 仍为 running | 表示上次未正常结束；启动管理服务会标记中断任务并恢复计划；不会恢复浏览器游标 |
